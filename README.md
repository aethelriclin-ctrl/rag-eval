# 最小 RAG 系统 + 四组评测实验（RAG Retrieval / Answer / Agentic / Lexical-vs-Semantic）

一个**从零手写**的 RAG 问答系统，以及**四组评测实验**：

| 实验 | 评什么 | 关键问题 |
| --- | --- | --- |
| **第 1 组** | **检索** | 找得到吗？ |
| **第 2 组** | **答案** | 答得对吗？引用靠得住吗？没有答案时会编吗？ |
| **第 3 组** | **Agent 的决策** | **它知道什么时候该查、什么时候不该查吗？** |
| **第 4 组** | **字面 vs 语义** | **换成向量检索，能比 BM25 找得更多吗？** |

重点不在于"我调通了 RAG"，而在于——

> **我能把一个"看起来在正常工作"的 RAG 系统测出它其实哪里不行，
> 然后定位根因、验证假设、把它修好，并且让修好的结果可复现。**
>
> **——同时也测出"我以为会更好的改动，其实没有更好"。**

---

## 一句话结论

> 知识库是我自己两个项目的文档（**7 个文件、42,114 字**，切成 **103 块**）。
> （这两个数可用 `rag/splitter.py` 的 `load_all_docs()` 直接数出来——
> 原先写的是"约 5 万字"，**实测 4.2 万，偏高了一档**，已按实测改正。）
>
> **最重要的发现是一个反直觉的现象**：
> 模型反复回答"资料中没有相关信息"，但答案明明在知识库里。
> 追下去发现真问题不在"找不到"，而在"**搜错了词**"——
> **BM25 把"哪几类""哪些"这类疑问词当成了关键词，而它们在文档里几乎不出现
> → IDF 极高 → 把真正的关键词挤了下去。**
> 加上**查询改写**之后，那几道"搜错词"的题确实被救回来了（检索分数涨 2~4 倍）。
> **⚠️ 但在 17 题全量上，改写并没有带来提升**——按配置指纹还原的分组是
> **有改写 7 轮均值 84.4% vs 无改写 4 轮均值 85.0%**（**有改写那组还略低 0.6 个点**），
> **两组分布完全重叠**。**之前写的"+25 个点"是拿 3 道题的试点数（58.3%）去比 17 题的数，不同口径，不可比。**
> 详见下文〈查询改写：一个被自己数据撤回的结论〉。
>
> **而第 4 组对照给出了相反的答案**：把 BM25 **整个换成语义检索（向量）**，
> 指标**一模一样**（26/28 = 26/28）——**语义检索在这个规模上没带来任何提升。**

| 指标 | 数值 |
| --- | --- |
| 检索 Recall@3（同义问法） | **100%**（17/17） |
| 检索 Recall@3（口语改写） | **92.9%**（26/28）——**BM25 与向量完全相同** |
| **答案正确率** | **82.5%**（3 轮区间 80.6%~83.5%） |
| **引用准确性** | **76.5%**（13/17） |
| **拒答率（1 − 幻觉率）** | **100%**（9/9：3 道应拒答题 × 3 轮，全部拒答） |
| **检索决策正确率** | **98.8%**（5 次全量观测合并 **84/85**；其中 3 轮稳定性跑测各 17/17） |
| **多余检索率** | **0%**（6 道"不该查"的题，历次跑测一次都没多此一举） |
| **漏查率** | **1/85**（9/24 首轮出现过 1 次，其余 4 次为 0） |

> **⭐ 而把"判断"和"生成"分开测之后，发现了一个更细的结论**：
> **二值决策是稳定的**（3 轮 17 题，查/不查零翻转），
> **而生成层措辞不稳定**（同一输入连跑 3 次，答案文本全都不一样）。
> **——噪声主要在"怎么写"，不在"要不要做"。**
>
> **⚠️ 但这两层的判据不对称，说的时候要收窄**（这是我在审计时发现的）：
> 生成层比的是**字符串全等**，决策层比的是**二值标志**。
> 而**同一份数据里，检索轮数其实变过**——a03 = 3/3/2、a07 = 4/4/5、a08 = 4/5/4、c01 = 3/2/2，
> **17 题里有 5 题**（漏数了一个：`c02 = 2/3/3` 也变过）。所以准确说法是：
> **"要不要查"零翻转；"查几轮"会变；"措辞"全变，但要点覆盖率只波动 2.9 个点。**

## 为什么要做这个

在项目 1（评测流水线）和项目 2（Agent 工具调用评测）里，我评的都是**别人的模型**。

做完之后我发现一个空白：

> **我会"评"，但没"建"过。**
> 而一个没亲手搭过 RAG 的人，评不出 RAG 的真问题——他只能评表面。

所以这个项目要做两件事：**① 自己搭一个能用的 RAG；② 然后评测它哪里不行。**

## 技术选择与理由

| 选择 | 理由 |
| --- | --- |
| **检索默认用 BM25（手写）** | 不需要任何模型或 API，完全可解释；也是"字面匹配"的基准线 |
| **同时实现了向量检索（语义匹配）** | 为了做对照实验——**同一批题，只换检索方式，看差多少**（见下方"第 4 组实验"） |
| **中文 2-gram 分词 + 停用字过滤** | 不装分词库。两字都是功能字（"的是""了这"）的碎片没有语义，只稀释权重 |
| **响应模型用 `deepseek-flash`** | 项目 3 的结论：同族模型精度无差异，没必要用贵的 |
| **embedding 用阿里云百炼 `text-embedding-v3`** | 兼容 OpenAI SDK；1024 维；**新用户 100 万 token 免费额度**（够本项目跑几十遍） |
| **块 500 字、重叠 50 字** | 见下方"对照实验"——这个值是**实测选出来的**（250 更差） |

### 找 embedding 的过程（如实记录，因为这段本身就是个结论）

**这个项目一开始**没有**向量检索**——不是不想要，是找不到能用的接口：

| 尝试 | 结果 |
| --- | --- |
| DeepSeek 官方 | ❌ **不提供 embedding 接口**（官方 API 文档无 Embeddings 一节；官方仓库 issue #806 亦确认） |
| 七牛云 AI | ❌ **404**——查官方文档后确认：它支持 `/v1/chat/completions`、`/v1/models`、`/v1/messages`，**没有 `/v1/embeddings`**。又用它自己的 `/v1/models` 列了全部 **81 个模型，无一个是 embedding 模型** |
| 第三方中转（Claude Code 中转站） | ❌ **Anthropic 本身不提供 embedding 服务** |
| **阿里云百炼（DashScope）** | ✅ **可用**——官方文档明确支持 OpenAI 兼容的 embeddings 接口 |

**⭐ 这段过程带来的两个后果**：

1. 🟡 **前 3 组实验都只有字面匹配**——所以"同义词替换会失效"这个限制，是被实测出来的，不是我推测的
2. ✅ **意外的收获**：正因为先只有字面匹配，**"疑问词污染"这个机制才被干净地观察到**——
   改写后单题的检索分数涨 **2~4 倍**，缺掉的要点排名从第 8~16 名升到第 1 名。
   如果一上来就用向量检索，这个问题会被语义匹配掩盖，反而测不出来。
   **⚠️ 但"机制被观察到"不等于"整体指标有提升"**——17 题全量上两组分布完全重叠，见下文那一节。

**⚠️ 另外记一条教训**：七牛那条线我**猜过两次地址**（`api.qnaigc.com`、`ai.qiniuapi.com`…），
两次都是 404。**正确做法是先去读官方文档，再动手试**——这跟项目 1 那句"答案钥必须验算"是同一类毛病。

## 评测设计

### 第 1 层：检索质量

**评测集每题标注「正确答案在哪个文件」**，判据是 top-k 里有没有来自该文件的结果。

**另有一套措辞敏感性测试**：同一件事用 4 种问法（文档原话 → 轻微改动 → 口语化 → 很短很口语），
因为**第一版评测集的用词和文档高度重合，等于照着答案出题**。

### 第 2 层：答案质量（三个指标）

| 指标 | 判据 |
| --- | --- |
| **答案正确率** | 答案覆盖了多少"期望要点"（关键词判分；`--llm` 时另跑一次 LLM 判分做对照） |
| **引用准确性** | 它声称"依据资料 1、3"——① 编号是否真实存在 ② **答案要点是否真出现在它引用的块里** |
| **拒答率** | "应拒答"的题里，明确说"资料中没有"的比例（**1 − 幻觉率**） |

> **引用准确性为什么查两层**：只查编号存在太松——**编造内容再随便挂个编号也能过**。

### 第 3 层：Agent 的检索决策（三个独有指标）

**这一层不再强制检索**——Agent 自己决定要不要调 `search_knowledge_base`。

| 指标 | 判据 |
| --- | --- |
| **决策正确率** | 该查的查了、不该查的没查 |
| **多余检索率** | **不该查却查了**（多此一举，浪费一次调用） |
| **漏查率** | **该查却没查**（更严重——它只能靠自己记忆答，那就可能编） |
| **决策翻转率** | 同一题跑多轮，"该不该查"的判断是否改变（**决策层的稳定性**） |

> **为什么只给 Agent 一个工具**：决策空间越小，"该不该查"这个判断才越纯粹；
> 工具一多，就分不清是"判断错"还是"选了别的工具"。

### 评测集规模

| 文件 | 题数 | 用途 |
| --- | --- | --- |
| `eval_set.json` | 17 可答 + 3 应拒答 | 第 1、2 层 |
| `eval_phrasing_set.json` | 7 组 × 4 问法 = 28 | 第 1 层措辞敏感性 |
| `eval_agentic_set.json` | 8 该查 + 6 不该查 + 3 库里没有 = 17 | 第 3 层决策 |

## 实验结果

### 第 1 层：检索

| 测试 | 结果 |
| --- | --- |
| 同义问法（Recall@3） | **17/17 = 100%** |
| 措辞改写（Recall@3） | **26/28 = 92.9%** |

**按问法位置拆开**：

| 位置 | 风格 | Recall@3 |
| --- | --- | --- |
| 0 | 文档原话 | 7/7 = 100% |
| 1 | 轻微改动 | 7/7 = 100% |
| 2 | 口语化 | 7/7 = 100% |
| **3** | **很口语/很短** | **5/7 = 71.4%** ⬇️ |

**失效的两个案例**：

| 问题 | 期望来源 | 实际命中 |
| --- | --- | --- |
| "那**八道题**都是什么类型的？" | 项目2-README.md | 项目2-失败案例.md |
| "换一种**打分方法**，结果会变吗？" | 项目2-README.md | 项目2-失败案例.md |

**注意第二个**：文档里写的是"**判分**方式"，用户问的是"**打分**方法"——**一字之差，2-gram 完全对不上。**

→ **BM25 能扛住句式改写，但扛不住关键词替换。它匹配的是"字"，不是"意思"。**

> **⚠️ 这条结论的证据强度要说清**（这是我在第 4 组实验之后回头补的）：
>
> | 证据 | 类型 |
> | --- | --- |
> | 上面这 2 个失败案例 | 🟡 **个体观察**（2 个样本，撑不起"规律"） |
> | 同一批 17 题上的**聚合指标** | ✅ **全量数字**——但**改写前后没有差异**（有改写 7 轮 84.4% vs 无改写 4 轮 85.0%，分布重叠） |
>
> **⭐ 这里更正一个我说过的错话。** 我原先写的是"**查询改写 +25 个点，是本结论的主证据**"——
> **这句话是错的**：那个 58.3% 来自 **3 道题的试点跑测**，83.5% 来自 **17 题全量**，
> **两个数不同口径、不可比**（原始文件里写着 `answerable: 3`）。**已撤回。**
>
> **改写确实修好了这条结论指向的那个机制**（改写后单题检索分数涨 2~4 倍），
> **但它在 17 题上的净提升是 0**——所以它**只能作为机制的可见样本，不能当作"提升"的证据**。

### ⚠️ 但第 1 层的 100% 是虚高的

**在做第 2 层时发现：模型反复回答"资料中没有相关信息"，可答案明明在文档里。**

**两个数字矛盾，于是写 `diagnose_retrieval.py` 查根因**——它不问"有没有命中正确文件"，
而问"**含答案要点的块，有没有真的落进喂给模型的 top-k 里**"：

| 诊断项 | 结果 |
| --- | --- |
| 答案要点存在于索引中 | **44/44 = 100%**（切分没问题） |
| **实际 top-5 内容覆盖的要点** | **35/44 = 80%** ⬇️ |
| 缺掉的要点 | **全是"成组出现的枚举"**（5 类评分器 / 4 类场景 / 四类归因） |

> **第 1 层的 Recall 判据太松**：一个文件被切成 30 块，混进任意一块就算命中——
> **它只保证"文件对"，不保证"块里有答案"。**
> 这是本项目第一个方法论教训：**尺子太松，量出来的数字好看但没用。**

### 对照实验：块大小 500 → 250（假设被证伪）

**假设**：500 字的块把"枚举表格"切散了 → 改小到 250 试试。

| 指标 | 块=500 | **块=250** |
| --- | --- | --- |
| 块数 | 103 | 230 |
| **top-5 覆盖要点** | **80%** | **70%** ⬇️ |
| 答案正确率 | 58.3%（n=3） | **33.3%**（n=3）⬇️ |
| 含答案块中位排名 | 1 | 2（最大 74 → 141） |

> **⚠️ 样本量说明**：**答案正确率那两行是 3 道题的试点跑测**（`--limit 3`，原始文件里 `answerable: 3`），
> **不是 17 题全量**；而"top-5 覆盖要点"那行是 17 题 / 44 个要点的全量统计。
> **两行口径不同，不要横着比。**（这正是我原先搞错的地方——见〈查询改写〉那一节。）

**❌ 假设被证伪，改回 500。**

**学到什么**：**块越小，语义越碎。** BM25 靠字面匹配，块被切碎后同一段内容的词分散到更多块，
每块的"信号密度"下降，反而更难被排上来。**在"字面匹配 + 2-gram"这个组合下，大块更稳。**

### ⭐ 查询改写：真正修好它的那一步

**重新看那个诊断**：缺的要点全是"枚举列表"，且分数被疑问词带偏。

**假设二**：**BM25 把"哪几类""哪些"当成了关键词，而它们在文档里几乎不出现 → IDF 极高 → 挤掉真关键词。**

**做法**：检索前先调一次模型，把问题改写成"文档里真会出现的词"。

| 问题 | 改写后的检索词 |
| --- | --- |
| 评测流水线实现了哪几类评分器？ | `评分器 判分 类型 exact 精确匹配 code 执行判分 json contains` |
| 失败归因机制把失败分成了哪几类？ | `失败归因 分类 能力不足 格式不合规 评分器误判 题目歧义` |

### 确定性：随机性从哪来

**同一套代码、同一套题连跑两次，结果不一样**（关键词 83.5%→80.6%，LLM 85.0%→77.2%）。
**跑两次结果不同，结论就不可信**，所以写了 `check_determinism.py` 拆开两个嫌疑：

| 嫌疑 | 测法 | 结果 |
| --- | --- | --- |
| ① 查询改写 | 同一问题改写 3 次，看检索词是否一致 | **2/3 不一致** ❌ |
| ② 生成端 | **把改写固定**，再生成 3 次 | **3/3 不一致** ❌ |

**① 是我自己引入的问题**——查询改写修好了"疑问词污染"，却带来了新的随机源。
**解法：把改写结果固化**（`data/rewrites.json`，首次问模型、之后永远读缓存）。

**固化后重测**：

| 检查 | 结果 |
| --- | --- |
| 查询改写一致性 | **0/3 不一致** ✅ 完全确定 |
| 生成端一致性 | 3/3 不一致（**`temperature=0` 不等于确定**） |

**而生成端带来的波动有多大？**（`measure_variance.py`：固定改写与检索，只重复生成 3 轮）

> **答案正确率区间只有 2.9 个点**（80.6% ~ 83.5%），16/17 道题三轮完全一致。

**所以**：**把可复现的部分固化之后，剩下的波动很小——但这个"很小"是测出来的，不是假设的。**

## 第 3 层：Agentic RAG（Agent 自主决定是否检索）

### 和第 2 层的区别

```
第 2 层：问题 → 【强制检索】 → 资料 → 生成
第 3 层：问题 → 【Agent 自己判断】 → 要查才查 → 生成
                      ↑
              多出来的这个"判断"，就是本层要评测的对象
```

### 评测设计

**只给 Agent 一个工具**（`search_knowledge_base`）——决策空间越小，"该不该查"这个判断才越纯粹。

**提示词里明确写清规则**（涉及项目事实必须查、通用常识/计算直接答、需要实时信息要说明局限）
——**先把规则说清，再测它守不守**。

**评测集 17 题，分三类**：

| 类别 | 题数 | 考什么 |
| --- | --- | --- |
| **该查**（a01–a08） | 8 | 项目事实、数字、结论 → 必须先检索 |
| **不该查**（b01–b06） | 6 | 计算 / 翻译 / 写代码 / 通用常识 → 直接答 |
| **库里没有**（c01–c03） | 3 | 库里没有答案 → 查完之后应当明确说不知道 |

### 结果

| 指标 | 数值 |
| --- | --- |
| **① 决策正确率** | **84/85 = 98.8%**（5 次全量观测合并：16/17 + 17/17 + 稳定性 3 轮各 17/17） |
| **② 多余检索率** | **0/6 = 0%**（6 道不该查的题，历次跑测一次都没多此一举） |
| **③ 漏查率** | **1/85**（9/24 首轮出现过 1 次漏查，其余 4 次为 0） |
| **④ 要点覆盖率** | **89.7% ~ 97.4%**（只有这两次记录了覆盖率：`172533` / `173130`；稳定性那 3 轮不记录覆盖） |
| **⑤ 拒答率（1 − 幻觉率）** | **3/3 = 100%** |
| **⑥ 引用准确性** | **7/8**（本轮；历轮在 5/5 ~ 7/8 之间，分母随"是否写了依据"而变） |

> **⚠️ 这里更正一个我原先的报法**：我先前只报了**最好那一轮**（17/17、漏查 0%）。
> **把 5 次全量观测合起来是 85 次决策、1 次漏查**——**准确说法是 98.8%，不是 100%。**
> **而"漏查 1/85"这件事本身是个发现**：我原先在"已知局限"里写"低频翻转需要更多轮次才看得见"，
> **其实那次低频漏查就在自己的数据里**——**这比我写"0%"要诚实，也更有信息量。**

**逐题决策全部符合预期**（17/17 🟢），包括最模糊的那几道：

| 题 | 期望 | 实际 | 说明 |
| --- | --- | --- | --- |
| "1+1 等于几？" | 不该查 | 没查 | 回答还附了理由："这是一个**通用常识**问题，不需要检索知识库" |
| "Python 里 list 和 tuple 最主要的区别？" | 不该查 | 没查 | ⭐ **最模糊的一题**——知识库里确实有 Python 相关内容，但它判断出这是通用常识 |
| "我的项目一共花了多少钱？" | 该查 | 查了 → 拒答 | ✅ **先查、再说"资料中没有"，顺序正确** |

### ⭐ 决策稳定性：把"判断"和"生成"分开测的收获

**`measure_decision_stability.py`：同一批题跑 3 轮，只看"该不该查"是否翻转。**

| 指标 | 结果 |
| --- | --- |
| **判断会翻转的题** | **0/17 = 0.0%** |
| **每轮决策正确率** | **100% / 100% / 100%** |
| **区间跨度** | **0.0 个点** |

**而对比第 2 层的同一件事**：

| 层面 | 3 轮一致性 |
| --- | --- |
| **决策**（该不该查） | ✅ **17/17 完全一致** |
| **生成**（答案怎么写） | ❌ **3/3 都不一致**（`check_determinism.py` 实测） |

> **结论：噪声源在"怎么写"，不在"要不要做"。**
> **Agent 的决策比它的措辞稳定得多。**

**这个结论只有把两层分开测才看得出来**——如果只测"最终答案对不对"，
两个层面的不稳定性会混在一起，谁也说不清噪声到底出在哪。

### 一个说明：为什么决策层比生成层稳

**我的推断（不是结论）**：决策是一个**二分类判断**（查 / 不查），输出空间极小，
而且提示词里给了明确规则；生成是**开放文本**，输出空间近乎无限。
**——输出空间越大，`temperature=0` 下的非确定性越容易显现。**

（**这个推断我没有单独验证**，如实标注在此。）

## 第 4 组实验：字面匹配 vs 语义匹配（BM25 vs 向量）

**这是本项目最后补上的一组对照**——前 3 组都只有 BM25，因为当时找不到可用的 embedding 接口。

**设计**：**同一批题、同一个脚本、同一套判据，只换检索器。**

| 检索器 | 原理 |
| --- | --- |
| **BM25** | 2-gram 字面匹配（词频 + IDF + 长度归一化） |
| **向量** | 阿里云百炼 `text-embedding-v3` → 1024 维向量 → 余弦相似度 |

### 结果：整体打平

| 指标 | BM25 | 向量 | 谁赢 |
| --- | --- | --- | --- |
| **Recall@3 同义问法** | 17/17 = **100%** | 17/17 = **100%** | 平 |
| **Recall@3 口语改写** | 26/28 = **92.9%** | 26/28 = **92.9%** | 平 |
| └ 第 0 种（文档原话） | 7/7 | 7/7 | 平 |
| └ 第 1 种（轻微改动） | **7/7** | 6/7 | BM25 |
| └ 第 2 种（口语化） | 7/7 | 7/7 | 平 |
| └ 第 3 种（很短口语） | 5/7 | **6/7** | 向量 |

**逐题差异只有 2 处，且分别落在两组不同的题目上**：

| 组 | BM25 | 向量 | 说明 |
| --- | --- | --- | --- |
| G6 Agent 评测集覆盖 | ✅✅✅❌ | ✅✅✅✅ | **向量对 1 题** |
| G7 判分方式差异 | ✅✅✅❌ | **✅❌✅❌** | **BM25 对 1 题（第 1 种问法）** |

### ⚠️ 我在这组实验里犯了两次"说过头"

**如实记下来，因为这两次修正本身就是结论的一部分**：

| 我先说的 | 数据实际支持的 | 修正 |
| --- | --- | --- |
| "向量应该能把 BM25 那 7.1% 的缺口补回来"（预期） | 总分**一模一样**（26/28） | ❌ **预期被否定** |
| "BM25 强在轻微改动、向量强在短口语 →**强项互补**" | **这 2 处差异是"题目"决定的，不是"问法类型"决定的**——2 个样本撑不起"互补"这个词 | 🟡 **收窄为"存在逐题差异，但样本不足以判断规律"** |

### 这组实验真正的结论

> **在"103 块语料 + 28 个问句变体"这个规模上，换用向量检索没有带来可测量的整体提升。**
>
> **——也就是说：BM25 在这个规模上已经够用；语义检索的价值要更大的语料、
> 更口语化的问法，或者更依赖"同义替换"的任务类型，才能体现出来。**

**⭐ 这是个负结果，但它是个真结论。而且它和项目 3 那条是同一个类型**：

> 项目 3："单价贵的模型（输入价 4.5 倍、输出价 3.4 倍，实测单题成本 1.85~12.71 倍），测出来没有精度收益。"
> 项目 4："语义检索，测出来没有整体召回收益。"
>
> **——"我认为应该更好的东西，测出来并没有更好。"**

**上面这张表里"第 1 种 vs 第 3 种"那个看着像规律的差别，很可能只是"这两题恰好各自属于 G6 和 G7"。**

## 已知局限

1. **默认检索器仍是字面匹配（BM25）**——向量检索已经接进链路做过对照（第 4 组），
   但**默认没换**，因为那个规模下测不出优势。同义替换的失效**实测到 2 例**（不是"必然失效"）
2. **向量对照只覆盖了检索层**——第 4 组比的是 Recall@3 与措辞命中，**生成层的向量对照（答案正确率）没做**，
   而 `rag/embedder.py` 的注释里原本承诺的正是这个。**这是真缺口，不是"已经做完"**
3. **停用字表是手写的**——不够系统，可能漏掉一些高频功能字
4. **2-gram 会产生无意义碎片**（"败归""因机"），目前只靠"两字都是功能字才丢"来过滤
5. **评测集只有 20 题**——数字能说明方向，不能当基准
6. **LLM 判分与被测系统同族**（都是 DeepSeek）——**存在"自己判自己"的效度隐患**，
   所以关键词判分仍作为主口径、LLM 判分作为对照
7. **查询改写缓存按问题原文索引**——新增问题仍会引入新改写，报告数字需注明"基于首次改写结果"
8. **第 3 层的引用核对是近似的**——Agent 可能检索多轮，而 `eval_agentic.py` 只拿
   **最后一次检索的块内容**去核对引用准确性。多轮场景下这个判据偏松
9. **没有测"漏查的后果"**——如果 Agent 该查却没查，它给出的答案是靠记忆还是有依据，
   这一层没有单独评测
10. **"决策比生成稳定"测了 5 次全量观测（85 次决策）**——能说明方向，不能当基准。
    **低频翻转已经观察到一次**：9/24 首轮出现过 **1 次漏查**（合并口径 84/85 = 98.8%）。
    更低的翻转率（<1%）需要更多轮次才看得见
11. **⚠️ 措辞测试只有 28 个变体——差 1 题就是 3.6 个百分点。**
    所以"字面 vs 语义只有 2 处差异"这个结论，**只能说"没有观察到整体差异"，
    不能说"两者完全等价"**。要判断有没有规律，需要把变体扩到 100+ 个
12. **向量检索只在 103 块语料上测过**——语料规模是影响语义检索效果的关键变量，
    这个规模下测不出优势，不代表更大规模下也测不出

## 我在这个项目里学到的东西

1. **"跑通"和"可用"是两件事。** 系统第一次端到端跑通时，我以为检索坏了——
   结果是我**测试问题**写得不好，不是检索坏了。
2. **冒烟测试只回答"能不能跑"，不回答"准不准"。** 我拿 5 个冒烟问题去下"检索质量"的结论，用错了工具。
3. **评测集的设计本身就是一门功夫。** 第一版用词和文档高度重合，等于照着答案出题——
   所以又补了一套"口语改写"的题。
4. **我的第一个假设是错的，而且数据当场就否定了它。** 我怀疑"块太大把表格切散"，
   改小之后各项指标全面变差。**一次只改一个变量，才能知道哪个变量真的有用。**
5. **尺子太松，量出来的数字好看但没用。** 第 1 层的 Recall 只查"文件对不对"，
   报出 100%；换成"块里有没有答案"之后，真实覆盖率只有 80%。
6. **我修好一个问题，引入了一个新问题。** 查询改写解决了疑问词污染，
   却让跑测结果不可复现。**修完之后要重测，不能假设"修好了就完了"。**
7. **`temperature=0` 不等于确定。** 这是我在三个项目里重复观察到的同一个事实
   （项目 2 的幻觉、项目 3 的成本波动、这里的答案质量）。
8. **报告要给区间，不给单点。** 因为单跑一次的数字没有代表性——
   **而"给区间"的前提是，我先测出了区间有多宽。**
9. **一个"边界"比一个"分数"值钱。** "Recall@3 = 100%"只是个分数；
   而"**BM25 扛得住句式改写、扛不住关键词替换**"是一条边界——**后者才能指导决策。**
10. **把"判断"和"生成"分开测，才看得清噪声出在哪。** 第 3 层测出决策 3 轮零翻转、
    生成 3 轮全翻转——**如果只测最终答案，这两个层面的不稳定会混在一起，谁也说不清。**
11. **我又一次从一次观察跳到了结论。** 第一次跑 Agent 评测得到 94.1% 的决策正确率，
    我立刻判断"Agent 的决策不稳定"；三组独立测量（17 题 × 3 轮）却显示 **0/17 翻转**。
    **一次观察不是结论——这条规矩我自己也还在练。**
12. **"我以为会更好"和"测出来更好"是两件事。** 第 4 组实验里，
    我预期"语义检索能补上 BM25 那 7.1% 的缺口"——**实测两者一模一样（26/28）。**
    **技术的"应该更好"必须先测，尤其在语料规模小的时候。**
13. **同一个毛病，我跨两个项目犯了四次。** 说 7.7 倍（无出处，实际项目在项目 1/3）、说"块太大"（被证伪）、
    说"强项互补"（2 个样本撑不起）、说"查询改写 +25 个点"（**3 题试点去比 17 题全量**）。
    **每次都是被追问，我才回头核对。**
    ——**"说过头"比"说错"更隐蔽，因为它听起来很合理。**
14. **负结果和正结果一样值钱。** 第 2 组（查询改写 = **0 个点**）和第 4 组（换检索方式 = **0 个点**），
    共同说明一件事：**在这个规模上，两个"听起来都该有用"的改进，实测都没有用。**
    **——而我能得出这个结论，是因为给每个改进都留了对照组。**

# 最小 RAG 系统 + 检索质量评测（RAG Retrieval & Answer Eval）

一个**从零手写**的 RAG 问答系统，以及一套**两层**的评测：先量检索、再量答案。

重点不在于"我调通了 RAG"，而在于——

> **我能把一个"看起来在正常工作"的 RAG 系统测出它其实哪里不行，
> 然后定位根因、验证假设、把它修好，并且让修好的结果可复现。**

---

## 一句话结论

> 知识库是我自己两个项目的文档（7 个文件、约 5 万字，切成 **103 块**），
> 检索用 **BM25**（纯本地手写：2-gram 分词 + 停用字过滤）。
>
> 评测下来最重要的发现是一个**反直觉的现象**：
> **模型反复回答"资料中没有相关信息"，但答案明明在知识库里。**
>
> 追下去发现真问题不在"找不到"，而在"**搜错了词**"：
> **BM25 把"哪几类""哪些"这类疑问词当成了关键词，而它们在文档里几乎不出现
> → IDF 极高 → 把真正的关键词挤了下去。**
>
> 加上**查询改写**（检索前先把问题改写成文档用词）之后：
> **答案正确率从 58.3% 提升到 83.5%。**

| 指标 | 数值 |
| --- | --- |
| 检索 Recall@3（同义问法） | **100%**（17/17） |
| 检索 Recall@3（口语改写） | **92.9%**（26/28） |
| **答案正确率** | **82.5%**（3 轮区间 80.6%~83.5%） |
| **引用准确性** | **76.5%**（13/17） |
| **拒答率（1 − 幻觉率）** | **100%**（资料中没有答案时，9/9 次全部拒答） |

## 为什么要做这个

在项目 1（评测流水线）和项目 2（Agent 工具调用评测）里，我评的都是**别人的模型**。

做完之后我发现一个空白：

> **我会"评"，但没"建"过。**
> 而一个没亲手搭过 RAG 的人，评不出 RAG 的真问题——他只能评表面。

所以这个项目要做两件事：**① 自己搭一个能用的 RAG；② 然后评测它哪里不行。**

## 技术选择与理由

| 选择 | 理由 |
| --- | --- |
| **检索用 BM25（手写）** | 不需要任何模型或 API，完全可解释；而且它是"字面匹配"的基准线，**能与未来的向量检索做对照** |
| **中文 2-gram 分词 + 停用字过滤** | 不装分词库。两字都是功能字（"的是""了这"）的碎片没有语义，只稀释权重 |
| **响应模型用 `deepseek-flash`** | 项目 3 的结论：同族模型精度无差异，没必要用贵的 |
| **块 500 字、重叠 50 字** | 见下方"对照实验"——这个值是**实测选出来的**（250 更差） |

### ⚠️ 为什么没用向量检索（如实说明）

**这是本项目一个必须讲清楚的限制**：

| 尝试 | 结果 |
| --- | --- |
| DeepSeek 官方 embedding | ❌ **不提供该接口**（已查证官方 API 文档无 Embeddings 一节；官方仓库 issue #806 亦确认） |
| 七牛云 | ❌ 404（**接口地址待核实**） |
| 第三方中转（Claude Code 中转站） | ❌ **Anthropic 本身不提供 embedding 服务** |

**所以先用 BM25 把链路跑通。** 这带来两个后果：

1. 🟡 **限制**：当前系统只有字面匹配能力，同义词替换会失效（已实测，见下）
2. ✅ **意外的收获**：正因为只有字面匹配，**"查询改写"这个改进的效果才被清楚地量化出来**
   （如果一开始就用了向量检索，疑问词污染的问题会被语义匹配掩盖，反而测不出来）

`rag/embedder.py` 已写好但**未接线**——拿到可用 embedding 后接进 `factory.py` 即可做对照。

```powershell

python tools\eval_phrasing.py       # 第 1 层：措辞敏感性
python tools\diagnose_retrieval.py  # 诊断：答案块排第几
```

## 评测设计

### 第 1 层：检索质量

**评测集每题标注「正确答案在哪个文件」**，判据是 top-k 里有没有来自该文件的结果。

**另有一套措辞敏感性测试**：同一件事用 4 种问法（文档原话 → 轻微改动 → 口语化 → 很短很口语），
因为**第一版评测集的用词和文档高度重合，等于照着答案出题**。

### 第 2 层：答案质量（三个指标）

| 指标 | 判据 |
| --- | --- |
| **答案正确率** | 答案覆盖了多少"期望要点"（关键词判分；`--llm` 时另跑一次 LLM 判分做对照） |
| **引用准确性** | 它声称"依据资料 1、3"——① 编号是否真实存在 ② **答案要点是否真出现在它引用的块里** |
| **拒答率** | "应拒答"的题里，明确说"资料中没有"的比例（**1 − 幻觉率**） |

> **引用准确性为什么查两层**：只查编号存在太松——**编造内容再随便挂个编号也能过**。

## 实验结果

### 第 1 层：检索

| 测试 | 结果 |
| --- | --- |
| 同义问法（Recall@3） | **17/17 = 100%** |
| 措辞改写（Recall@3） | **26/28 = 92.9%** |

**按问法位置拆开**：

| 位置 | 风格 | Recall@3 |
| --- | --- | --- |
| 0 | 文档原话 | 7/7 = 100% |
| 1 | 轻微改动 | 7/7 = 100% |
| 2 | 口语化 | 7/7 = 100% |
| **3** | **很口语/很短** | **5/7 = 71.4%** ⬇️ |

**失效的两个案例**：

| 问题 | 期望来源 | 实际命中 |
| --- | --- | --- |
| "那**八道题**都是什么类型的？" | 项目2-README.md | 项目2-失败案例.md |
| "换一种**打分方法**，结果会变吗？" | 项目2-README.md | 项目2-失败案例.md |

**注意第二个**：文档里写的是"**判分**方式"，用户问的是"**打分**方法"——**一字之差，2-gram 完全对不上。**

→ **BM25 能扛住句式改写，但扛不住关键词替换。它匹配的是"字"，不是"意思"。**

### ⚠️ 但第 1 层的 100% 是虚高的

**在做第 2 层时发现：模型反复回答"资料中没有相关信息"，可答案明明在文档里。**

**两个数字矛盾，于是写 `diagnose_retrieval.py` 查根因**——它不问"有没有命中正确文件"，
而问"**含答案要点的块，有没有真的落进喂给模型的 top-k 里**"：

| 诊断项 | 结果 |
| --- | --- |
| 答案要点存在于索引中 | **44/44 = 100%**（切分没问题） |
| **实际 top-5 内容覆盖的要点** | **35/44 = 80%** ⬇️ |
| 缺掉的要点 | **全是"成组出现的枚举"**（5 类评分器 / 4 类场景 / 六类归因） |

> **第 1 层的 Recall 判据太松**：一个文件被切成 30 块，混进任意一块就算命中——
> **它只保证"文件对"，不保证"块里有答案"。**
> 这是本项目第一个方法论教训：**尺子太松，量出来的数字好看但没用。**

### 对照实验：块大小 500 → 250（假设被证伪）

**假设**：500 字的块把"枚举表格"切散了 → 改小到 250 试试。

| 指标 | 块=500 | **块=250** |
| --- | --- | --- |
| 块数 | 103 | 230 |
| **top-5 覆盖要点** | **80%** | **70%** ⬇️ |
| 答案正确率 | 58.3% | **33.3%** ⬇️ |
| 含答案块中位排名 | 1 | 2（最大 74 → 141） |

**❌ 假设被证伪，改回 500。**

**学到什么**：**块越小，语义越碎。** BM25 靠字面匹配，块被切碎后同一段内容的词分散到更多块，
每块的"信号密度"下降，反而更难被排上来。**在"字面匹配 + 2-gram"这个组合下，大块更稳。**

### ⭐ 查询改写：真正修好它的那一步

**重新看那个诊断**：缺的要点全是"枚举列表"，且分数被疑问词带偏。

**假设二**：**BM25 把"哪几类""哪些"当成了关键词，而它们在文档里几乎不出现 → IDF 极高 → 挤掉真关键词。**

**做法**：检索前先调一次模型，把问题改写成"文档里真会出现的词"。

| 问题 | 改写后的检索词 |
| --- | --- |
| 评测流水线实现了哪几类评分器？ | `评分器 判分 类型 exact 精确匹配 code 执行判分 json contains` |
| 六类失败归因机制把失败分成了哪几类？ | `失败归因 分类 能力不足 格式不合规 评分器误判 题目歧义` |

**效果——缺掉的要点排名直接从第 8~16 名升到第 1 名**：

| 要点 | 改写前排名 | 改写后排名 |
| --- | --- | --- |
| `exact` / `code` | 第 16 名 | **第 1 名** |
| `能力不足` / `格式不合规` / `评分器误判` / `题目歧义` | 第 8 名 | **第 1 名** |

**最终效果**：

| 指标 | 无改写 | **有改写** |
| --- | --- | --- |
| **答案正确率** | 58.3% | **83.5%** ⬆️ +25 个点 |
| 引用准确性 | 33.3% | **76.5%** |

### 第 2 层：答案质量（最终数字）

| 指标 | 数值 |
| --- | --- |
| **答案正确率（关键词判分）** | **82.5%**（3 轮：83.5 / 83.5 / 80.6，**区间 80.6%~83.5%**） |
| 答案正确率（LLM 判分） | 77.2% ~ 85.0%（波动较大） |
| **引用准确性** | **13/17 = 76.5%** |
| **拒答率（1 − 幻觉率）** | **9/9 = 100%**（3 道应拒答题 × 3 轮，全部拒答） |

**逐题稳定性**：3 轮里只有 **1/17** 道题的覆盖变过（q10：100% / 100% / 50%）。

### 两种判分方式的对照

| 题 | 关键词判分 | LLM 判分 | 谁对 |
| --- | --- | --- | --- |
| q09 难度分层题库包含哪几类 | 25% | **0%** | **LLM 对**——关键词**假阳性**（文本碰巧含"推理"二字） |
| q16 三轮幻觉实验结论 | **100%** | **67%** | **LLM 对**——关键词说全中，实际缺要点 |

**两处都是"关键词判分偏高"。** 这是我在项目 1 里担心过的反向问题：
**关键词匹配会放进假阳性——原文里出现过关键词，不等于模型答对了。**

### 确定性：随机性从哪来

**同一套代码、同一套题连跑两次，结果不一样**（关键词 83.5%→80.6%，LLM 85.0%→77.2%）。
**跑两次结果不同，结论就不可信**，所以写了 `check_determinism.py` 拆开两个嫌疑：

| 嫌疑 | 测法 | 结果 |
| --- | --- | --- |
| ① 查询改写 | 同一问题改写 3 次，看检索词是否一致 | **2/3 不一致** ❌ |
| ② 生成端 | **把改写固定**，再生成 3 次 | **3/3 不一致** ❌ |

**① 是我自己引入的问题**——查询改写修好了"疑问词污染"，却带来了新的随机源。
**解法：把改写结果固化**（`data/rewrites.json`，首次问模型、之后永远读缓存）。

**固化后重测**：

| 检查 | 结果 |
| --- | --- |
| 查询改写一致性 | **0/3 不一致** ✅ 完全确定 |
| 生成端一致性 | 3/3 不一致（**`temperature=0` 不等于确定**） |

**而生成端带来的波动有多大？**（`measure_variance.py`：固定改写与检索，只重复生成 3 轮）

> **答案正确率区间只有 2.9 个点**（80.6% ~ 83.5%），16/17 道题三轮完全一致。

**所以**：**把可复现的部分固化之后，剩下的波动很小——但这个"很小"是测出来的，不是假设的。**

## 已知局限

1. **只有字面匹配**——同义词替换必然失效（已实测）。这是本项目最大的功能限制
2. **没有向量检索对照**——因 DeepSeek 无 embedding、第三方 key 未通（详见上文）
3. **停用字表是手写的**——不够系统，可能漏掉一些高频功能字
4. **2-gram 会产生无意义碎片**（"败归""因机"），目前只靠"两字都是功能字才丢"来过滤
5. **评测集只有 20 题**——数字能说明方向，不能当基准
6. **LLM 判分与被测系统同族**（都是 DeepSeek）——**存在"自己判自己"的效度隐患**，
   所以关键词判分仍作为主口径、LLM 判分作为对照
7. **查询改写缓存按问题原文索引**——新增问题仍会引入新改写，报告数字需注明"基于首次改写结果"

## 我在这个项目里学到的东西

1. **"跑通"和"可用"是两件事。** 系统第一次端到端跑通时，我以为检索坏了——
   结果是我**测试问题**写得不好，不是检索坏了。
2. **冒烟测试只回答"能不能跑"，不回答"准不准"。** 我拿 5 个冒烟问题去下"检索质量"的结论，用错了工具。
3. **评测集的设计本身就是一门功夫。** 第一版用词和文档高度重合，等于照着答案出题——
   所以又补了一套"口语改写"的题。
4. **我的第一个假设是错的，而且数据当场就否定了它。** 我怀疑"块太大把表格切散"，
   改小之后各项指标全面变差。**一次只改一个变量，才能知道哪个变量真的有用。**
5. **尺子太松，量出来的数字好看但没用。** 第 1 层的 Recall 只查"文件对不对"，
   报出 100%；换成"块里有没有答案"之后，真实覆盖率只有 80%。
6. **我修好一个问题，引入了一个新问题。** 查询改写解决了疑问词污染，
   却让跑测结果不可复现。**修完之后要重测，不能假设"修好了就完了"。**
7. **`temperature=0` 不等于确定。** 这是我在三个项目里重复观察到的同一个事实
   （项目 2 的幻觉、项目 3 的成本波动、这里的答案质量）。
8. **报告要给区间，不给单点。** 因为单跑一次的数字没有代表性——
   **而"给区间"的前提是，我先测出了区间有多宽。**
9. **一个"边界"比一个"分数"值钱。** "Recall@3 = 100%"只是个分数；
   而"**BM25 扛得住句式改写、扛不住关键词替换**"是一条边界——**后者才能指导决策。**

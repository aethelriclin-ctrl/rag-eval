# 最小 RAG 系统 + 检索质量评测（RAG Retrieval Eval）

一个**从零手写**的 RAG 问答系统，以及一套针对**检索质量**的评测。

重点不在于"我调通了 RAG"，而在于——

> **我能量化一个检索方案的能力边界：它在什么问法下会失效，失效在哪里。**

---

## 一句话结论

> 知识库是我自己的两个项目文档（7 个文件、约 5 万字），切成 **103 块**。
> 检索用 **BM25**（纯本地手写，2-gram + 停用字过滤）。
>
> **同义问法下 Recall@3 = 17/17 = 100%**；
> **但把问题改写成日常口语后，掉到 26/28 = 92.9%**——
> **失效全部集中在"关键词被整体替换"的那一档（71.4%）。**
>
> 而且这 17 道题里，**模型在资料确实没有答案时，5 次全部拒答**（0 次编造）。

---

## 为什么要做这个

在项目 1（评测流水线）和项目 2（Agent 工具调用评测）里，我评的都是**别人的模型**。

做完之后我发现一个空白：

> **我会"评"，但没"建"过。**
> 而一个没亲手搭过 RAG 的人，评不出 RAG 的真问题——他只能评表面。

所以这个项目要做两件事：**① 自己搭一个能用的 RAG；② 然后评测它哪里不行。**

---

## 技术选择与理由

| 选择 | 理由 |
| --- | --- |
| **检索用 BM25（手写）** | 不需要任何模型或 API，完全可解释；而且它是"字面匹配"的基准线，能和未来的向量检索做对照 |
| **中文 2-gram 分词** | 不装分词库。2-gram（"失败归因" → "失败/败归/归因"）能捕捉词边界 |
| **停用字过滤** | 两字都是功能字（"的是""了这"）的碎片没有语义，只稀释权重 |
| **响应模型用 `deepseek-flash`** | 项目 3 的结论：同族模型精度无差异，没必要用贵的 |
| **切 500 字/块、重叠 50 字** | 500 是语义完整性和检索精度的折中；重叠是为了避免答案横跨块边界时"两边都只拿到半句" |

> ⚠️ **为什么没用向量检索**：DeepSeek 官方不提供 embedding 接口（已查证官方 API 文档）。
> 试过两个第三方中转的 key，地址未通。所以先用 BM25 把链路跑通 ——
> **这正是本项目要评测的对象：字面匹配的能力边界在哪。**

```powershell
$env:DEEPSEEK_API_KEY="你的key"

python main.py --build             # ② 建索引（纯本地，不花钱）
python main.py --test              # ③ 冒烟测试（5 问）
```

依赖：Python 3.x + `openai`。**检索本身不需要 numpy**（BM25 是纯 Python 实现）。

## 评测设计（这是本项目的核心）

### ① 检索评测：Recall@k

**评测集 `eval_set.json` 的每一题都标了「正确答案在哪个文件」**：

```json
{
  "id": "q01",
  "question": "我的评测项目一共有几道题？",
  "expected_sources": ["项目1-README.md"]
}
```

**判据**：top_k 的检索结果里，**至少有一个来源命中 `expected_sources`**。

**为什么要标注而不是肉眼看**：没有刻度就只能说"好像好一点"；有了它才能报出"召回率从 X% 到 Y%"。

### ② 措辞敏感性测试

**同一件事，四种问法，从"文档原话"到"日常口语"**：

| 位置 | 风格 | 例子 |
| --- | --- | --- |
| 0 | 文档原话 | "单题成本在多次跑测之间会波动多少倍？" |
| 1 | 轻微改动 | "跑一次大概要花多少钱？" |
| 2 | 口语化 | "这个成本稳定吗？" |
| 3 | 很口语/很短 | "费用会不会差很多？" |

**为什么要这个**：评测集里的问题用词和文档高度重合，**相当于照着答案出题**。
真实用户不会用文档里的原话提问。

### ③ 防幻觉测试

**评测集里有 3 题是"文档里绝对没有的"**（花了多少钱、用哪家 GPU、作者多大）。
它们测的不是"找得到"，而是**"找不到时会不会编"**。

## 实验结果

### 检索质量（Recall@3）

| 测试 | 结果 |
| --- | --- |
| 同义问法（`eval_retrieval.py`） | **17/17 = 100.0%** |
| 措辞改写（`eval_phrasing.py`） | **26/28 = 92.9%** |

### 按问法位置拆开

| 位置 | 风格 | Recall@3 |
| --- | --- | --- |
| 0 | 文档原话 | **7/7 = 100%** |
| 1 | 轻微改动 | **7/7 = 100%** |
| 2 | 口语化 | **7/7 = 100%** |
| **3** | **很口语/很短** | **5/7 = 71.4%** ⬇️ |

### 失效的两个案例

| 问题 | 期望来源 | 实际命中 | 最高分 |
| --- | --- | --- | --- |
| "那**八道题**都是什么类型的？" | 项目2-README.md | 项目2-失败案例.md | 6.35 |
| "换一种**打分方法**，结果会变吗？" | 项目2-README.md | 项目2-失败案例.md | 6.60 |

**注意第二个**：文档里写的是"**判分**方式"，用户问的是"**打分**方法"——
**一字之差，2-gram 完全对不上，检索失效。**

### ⭐ 核心发现（这是本项目最值钱的结论）

> **BM25 的成败，取决于改写后是否还留下至少一个"文档里出现过的关键词"。**
>
> - **句式怎么改都没事**（位置 0~2 全部 100%）
> - **一旦关键词被整体替换**（判分→打分、八道题→那些题），**立刻失效**（位置 3 掉到 71.4%）
>
> **换句话说：它匹配的是"字"，不是"意思"。**
> **而这精确地划出了字面匹配的能力边界——也就是"为什么需要向量检索"。**

### 防幻觉

| 测试 | 结果 |
| --- | --- |
| 资料中确实没有答案的 3 题 | **全部拒答（0 次编造）** |
| 冒烟测试的 2 道无答案题 | **全部拒答** |

生成端的提示词里有一条硬约束：

> "只根据下面提供的资料回答；如果资料里没有足够信息，直接回答'资料中没有相关信息'。"

**实测这条约束是生效的**——而且拒答时它还会说明理由，例如：

> "依据资料 1、2、3，均未提及项目的作者姓名。"

## 已知局限

1. **检索只有字面匹配**——同义词替换必然失效（已实测，见上文）
2. **块大小 500 字未做对照实验**——250 / 500 / 1000 哪个更好，还没测
3. **停用字表是手写的**——不够系统，可能漏掉一些高频功能字
4. **2-gram 会产生无意义碎片**（"败归""因机"）——目前靠"两字都是功能字才丢"来过滤，粒度较粗
5. **评测集只有 20 题**——数字能说明方向，不能当基准
6. **没有向量检索对照**——因为 DeepSeek 无 embedding 接口，第三方 key 未通

## 我在这个项目里学到的东西

1. **"跑通"和"可用"是两件事。** 系统第一次端到端跑通时，我以为检索坏了——结果是我的**测试问题**写得不好，不是检索坏了。
2. **冒烟测试只回答"能不能跑"，不回答"准不准"。** 我拿 5 个冒烟问题去下"检索质量"的结论，用错了工具。**要下质量结论，必须有标注好的评测集。**
3. **评测集的设计本身就是一门功夫。** 我的第一版评测集用词和文档高度重合，等于照着答案出题——**所以又补了一套"口语改写"的题**。
4. **换实现时要顺手清掉不再需要的依赖。** 改用 BM25 后 `numpy` 已经没用，但那行 import 还在，直接把主流程卡住了。
5. **改一个变量，看一个结果。** 加停用字过滤后召回率没变（词数只降 5%），说明**我原来猜的原因不是主因**——先改一个再测，才知道真正的原因在哪。
6. **一个"边界"比一个"分数"值钱。** "Recall@3 = 92.9%"只是个分数；而"**失效集中在关键词被整体替换时**"是一条边界——**后者才能指导决策。**
